# Architecture

Status: **approved baseline for phase 1**.

## Repository shape

Use a single monorepo with three independently deployable applications:

```text
apps/
├── web/      # public website, initialized now
├── admin/    # admin panel, create only after the admin scope is approved
└── api/      # backend, create only after the API/domain model is approved

packages/
├── contracts/      # API DTO schemas and inferred TypeScript types
├── config-eslint/  # shared lint configuration when the second app appears
├── config-ts/      # shared TypeScript configuration when the second app appears
└── ui/             # only genuinely shared primitives, not website sections
```

The repository uses **npm workspaces** initially. This keeps setup small and uses the existing lockfile. Add Turborepo only when parallel builds, remote caching, or CI duration justify it.

## Application boundaries

### Public website (`apps/web`)

- Next.js App Router and TypeScript.
- Primarily React Server Components.
- Static generation for stable marketing pages.
- Incremental revalidation for CMS-managed content.
- Client Components only for interactive islands: forms, menus, sliders and filters.
- Public read requests go directly to the API through a typed server-side client.
- Lead forms are sent through a same-origin Next.js route handler/BFF to avoid exposing backend details and to add anti-spam controls.

### Admin panel (`apps/admin`, deferred)

- A separate Next.js application and deployment.
- Protected routes and an independent admin domain, for example `admin.smartum.kiev.ua`.
- Feature-oriented modules rather than reusing public-site page components.
- May share contracts, tokens and low-level UI primitives with the website.
- Must not share its authentication/session logic with the public website bundle.

### API (`apps/api`, deferred)

- NestJS modular monolith.
- PostgreSQL as the source of truth.
- Prisma for schema, migrations and database access.
- REST API with an OpenAPI specification.
- Domain modules are expected to start with: `auth`, `users`, `courses`, `locations`, `pages`, `leads`, `media`, `settings`.
- Background jobs and queues are not added until a concrete workflow requires them.

## Approved library policy

Install a library only in the app that uses it. Do not put runtime dependencies in the monorepo root.

| Concern | Decision |
| --- | --- |
| Package management | npm workspaces |
| Public site and admin | Next.js + React + TypeScript |
| API | NestJS + TypeScript |
| Database | PostgreSQL |
| ORM/migrations | Prisma |
| Styling | Tailwind CSS plus semantic CSS custom properties |
| Accessible primitives | Radix UI, added per component only |
| Icons | Lucide React |
| Forms | React Hook Form |
| Shared validation/contracts | Zod; Nest integration decided with the API bootstrap |
| Public data fetching | Native Next.js `fetch` with cache/revalidation |
| Admin server state | TanStack Query, only when admin work starts |
| Local client state | React state first; Zustand only for demonstrated cross-page UI state |
| API documentation | OpenAPI/Swagger generated by NestJS |
| API logging | Pino via `nestjs-pino` |
| Unit tests | Vitest for shared/frontend logic; Jest can remain Nest's default if migration has no benefit |
| Browser tests | Playwright for critical public and admin flows |

Not approved by default: a general-purpose global state store for the public site, GraphQL, a microservice split, a queue, or a component suite that dictates the visual language.

## Contracts and data flow

`packages/contracts` will contain framework-neutral Zod schemas and inferred TypeScript types. It must not import NestJS, Next.js, Prisma, or browser-only code.

Prisma models remain private to the API. Frontends consume public DTOs, never generated Prisma types. This prevents database changes from leaking into UI code.

```text
PostgreSQL ← Prisma ← NestJS modules ← REST/OpenAPI
                                      ↑
                         contracts schemas/types
                                      ↓
                      Next.js web / Next.js admin
```

## Design-system direction

The design system will be implemented inside `apps/web` first. It is not promoted to `packages/ui` until the admin panel needs the same primitive and the shared API is proven.

Layers:

1. **Foundations** — color, typography, spacing, radius, shadow, breakpoint and motion tokens.
2. **Primitives** — Button, Container, Stack, Cluster, Heading, Text, Input, Textarea.
3. **Composites** — Header, Footer, CourseCard, LeadForm, SectionHeading.
4. **Sections/pages** — website-specific composition; never exported as generic UI.

Tokens use semantic names such as `--color-surface-brand` and `--space-section`, not page-specific names such as `--hero-purple`.

## Routing baseline for the public website

```text
/
/courses
/courses/[slug]
/about
/contacts

# planned after content approval
/locations
/locations/[slug]
/blog
/blog/[slug]
/privacy
```

Route slugs remain in English for stable technical URLs. Visible labels and metadata are Ukrainian. Redirects are required whenever an existing indexed URL changes.

## Environment policy

- Root contains no application secrets.
- Each application owns `.env.example` and validates its environment at startup.
- Browser-exposed variables must use the `NEXT_PUBLIC_` prefix deliberately.
- Database credentials and signing secrets exist only in the API deployment.

## Deployment model

Each application has an independent build and deployment pipeline. A change in the website must not require deploying the API or admin panel. Production domains are expected to be:

- `smartum.kiev.ua` — web;
- `admin.smartum.kiev.ua` — admin;
- `api.smartum.kiev.ua` — API.
